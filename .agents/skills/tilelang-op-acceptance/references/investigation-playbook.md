# 排查手册：小形对、目标形错

本文件是 `tilelang-op-acceptance` 场景 C 的完整走查（SKILL.md §5.4 的展开）。

**总则**：每一步**只动一个变量**，每步都**自带一个已知-good 的对照**，
且**判读规则在跑之前写下**——跑完只对账，不解释。理由：事后解释是"把结果讲圆"，不是验证。

---

## 0. 先做什么（30 分钟的准备工作）

动手之前，先把"错在哪一层"的空间画出来，否则会一直在同一层打转：

```text
host 胶水（torch 侧）：切片 / 广播 / 累加 / dtype 转换 / 分块参数
   └─ 前置件 A：cumsum、solve_a（求逆）、scan1（状态扫描）
        └─ 前置件 B：20 个单职责 kernel
             └─ 后置：输出写入（逐 chunk 写 / cat）
```

**关键**：错误通常在**最上游的那个"看起来没问题"的环节**。本项目真凶在最上游的
`solve_a`（一个 64×64 的求逆里的分块循环），而它之前已经被"验过"。

---

## 1. 第 1 步：是 kernel 还是前置件？

### 问题

底层 20 个 kernel 的数值，与"它们被组合起来"之后的数值，哪个错？

### 做法

给 relay 加两个"注入参考中间量"的入参（本项目为 `hs_override` / `a_override`），
把 golden 算出的中间量直接灌进去。这是**唯一一种**能把前置件从链路里摘掉的干净手段。

```python
# 灌 golden 的 H_in / A：若结果变好 ⇒ 前置件（或它之前的输入）有问题
out = relay(q, k, v, g, beta, h0, do, chunk_size=C,
            hs_override=golden_hin, a_override=golden_a)
```

### 判读表

| 观察 | 含义 | 下一步 |
|---|---|---|
| 灌了就变好 | 前置件错 | 第 2 步 |
| 灌了**没变** | 前置件不是主因 ⇒ 组合层/kernel/胶水 | 第 4 步 |
| 灌了**一半变好** | 有两个错误源，别急着下结论 | 分别验：先只灌 H，再只灌 A |
| 灌了**部分量变好、部分不变** | 与"该量是否经过被灌的中间量"有关 | 画数据流表（见下） |

### 数据流表（本项目实例）

| 量 | 经过 `H_in`？ | 经过 `A`？ |
|---|---|---|
| `dh0` | 否 | 是（经 `wm = A·x`） |
| `dq` | 是 | 是 |
| `dv` | 是 | 是 |
| `dk` | 是 | 是 |

> ⚠️ **这张表本身是断言**，必须能被实验证伪。本项目就有一条"`dh0` 不经过 `H_in`"的推断，
> 后来被实测推翻（灌 `H_in` 后 `dh0` 变了 5 倍）。**数据流表写出来要用一次实验对上，
> 对不上就以实验为准。**

## 2. 第 2 步：前置件的哪个分块参数退化了？

### 问题

前置件是分块实现的（`for i in T.serial(ceildiv(X, BX))`）。块数 = 1 时循环体只跑一次，
**里面写错也看不出来**。

### 做法

扫分块参数，每次只改一个，与同一个 golden 比：

```python
for BK in (64, 128):                    # 只改这一个数
    ws_a = solve_a(B, H, T, DK, C, BK, dtype="float16")(k, beta, ws_g, msk_j, idt)
    print(f"BK={BK}  A 误差={rel_vs_golden(ws_a, golden_a):.3e}")
```

### 判读表

| 观察 | 含义 |
|---|---|
| 块数 1 的配置对、块数 >1 的错 | 循环体内的路径有缺陷（G4） |
| 两种块数都错 | 不是分块问题，继续第 3/4 步 |
| 两种块数都对但端到端仍错 | 前置件清白，问题在下游 |

### 本项目实测

```
DK=128 BK=64 （bk_num=2）  A 误差 1.388e-01
DK=128 BK=128（bk_num=1）  A 误差 5.961e-05     ← 2330×
```

## 3. 第 3 步：是"数值宽度"还是"代码分支"？

### 问题

改形状时**代码可能切到另一条分支**。此时"改形状"不是一个变量而是两个。

### 做法

在源码里 `grep` 所有依赖形状的 `if/elif`：

```bash
grep -n "DV == C\|DK == C\|if .*shape\|elif" <kernel 文件>
```

本项目实例（`gdn_bwd_v3.py`）：

```python
if DV == C:   dkt = k_ab_dv(v_hi, nxt_delta) + ...     # DV=64 走这条
else:         dkt = k_mm   (v_hi, nxt_delta) + ...     # DV=128 走这条
```

⇒ `DK/DV 64→128` 同时改了**数值宽度**与**分支**。所以后续实验要么固定形状只改分块参数
（第 2 步），要么把两条分支都覆盖。

### 判读表

| 情况 | 处理 |
|---|---|
| 分支各自的算子在核级都 PASS | 分支不是问题，回到第 1/2 步 |
| 某分支只在大宽度下走，且从未被单测 | 该分支是"未覆盖路径"，优先怀疑但它不是结论 |

## 4. 第 4 步：核级单元对拍（定位到具体 kernel）

### 做法

绕开整个组合层，逐个 kernel 喂已知输入，与 golden 的**同名中间量**比。
必须**同时跑小形状与目标形状**（否则分不清是"形状"还是"这个 kernel"）。

```python
# 骨架：每个 kernel 一条 (输入 -> 参考) 的对照
cases = {
    "raw":  lambda: k_raw(Qc, Kc),                      ref: cache["q"] @ cache["k"].T,
    "P":    lambda: k_gate(raw, Gamc, msk),             ref: cache["p_mat"],
    "vnew": lambda: k_vnew(Ac, bv, wm, Hc),             ref: cache["vnew"],
    "qh":   lambda: k_tb(Qc, Hc),                       ref: cache["qh"],
}
# 先跑 64 形的 CONTROLS（必须 PASS），再跑目标形状
```

### 判读表

| 观察 | 结论 |
|---|---|
| CONTROL（小形）全 PASS，目标形全 PASS | kernel 清白 ⇒ 去查胶水层（切片/广播/dtype/写入路径） |
| 小形 PASS、目标形个别 FAIL | 该 kernel 的形状相关缺陷（或它走的分支） |
| CONTROL 就 FAIL | **探针错**，回到 gate G5 |

### 本项目实测（14 格，全部 ≤3.4e-04）

```
CONTROL mm(64,64) 2.5e-04 PASS   CONTROL ta(64,64) 2.2e-04 PASS
CONTROL ta32(64,64)6.9e-08 PASS  CONTROL tb(64,64) 2.6e-04 PASS
CONTROL raw(DK=64) 2.6e-04 PASS  CONTROL ta32(128,128) 7.4e-08 PASS
WIDE mm(128,128) 3.3e-04 PASS    WIDE ta(64,128) 2.3e-04 PASS
WIDE ta(128,128) 3.1e-04 PASS    WIDE tb(128,128) 3.4e-04 PASS
WIDE raw(DK=128) 2.8e-04 PASS
```

结论：20 个 kernel 在 128 下无罪 ⇒ 直接跳到第 1 步的结论"前置件"，排除了整层。

## 5. 四个真实案例的完整走查

### 案例 A：用"核级 14 格"一次排除两层

- 疑点：宽 tile（128）+ fp16 落 GM 是不是有问题？
- 手段：`_wide_tile_probe`，6 条 CONTROL（已实测好的格）+ 8 个待判定格
- 结果：14 格最大 3.4e-04
- **收益**：`k_mm(128,128)` 与"fp16 宽落盘"两个假设同时死，省下至少两轮排查

### 案例 B：`A` 差 14%，而 `dq` 只差 4e-4 —— 先怀疑探针

- 现象：探针报"中间量 `A` 差 1.39e-01"，但同一配置下 `dq` 只有 4e-04
- 当时的第一反应（错）：改算子
- 正确动作：**两个数字互相矛盾 ⇒ 先验证量具**。给探针补 64 形 CONTROL：
  ```
  DK=64  a_rel=5.9e-05  ok      ← 量具在已知-good 配置上是准的
  DK=128 a_rel=1.39e-01 SUSPECT ← 这个 FAIL 才有意义
  ```
- **收益**：把"探针可能错"变成"探针已验证"，同一个数字从噪声变成证据

### 案例 C：块数退化——真凶藏了四个星期

- 现象：`DK=128` 时 `A` 差 14%，`DK=64` 时 5.9e-05
- 手段：只改 `BK`（64 → 128），`A` 回到 5.96e-05
- 机理：`DK=64` 时 `ceildiv(64,64)=1`，循环体只跑 `i=0`，`i>0` 的两条路径从未执行
- **收益**：定位到"参数覆盖"而非"形状覆盖"这一整类盲区（G4）

### 案例 D：先排除"看起来更可疑"的那一层

- 现象：`DK=DV=128` 下五项 5%~12%，只有 `dh0` 好
- 先后被排除：H 数（H=1 一样坏）、chunk 数（4 chunk 也坏）、`H_in`（灌 golden 无效）、
  golden（两套互查 1e-15）、h0（示例本身就用非零 h0）、片上预算（静态累加达标）、
  探针方法学（同探针在 64 复现 1e-3）
- **收益**：把"可能有七种原因"收敛到一种，代价是 7 条单变量数据

## 6. 反面教材：三条被推翻的假设（以及下次怎么避免）

| 假设 | 依据（当时） | 被什么推翻 | 下次的检查 |
|---|---|---|---|
| "`dk` 参与跨 chunk 递推，要给它加 fp32 中转" | 读代码后的推断 | 代码里 `dk` 只写不读 | 结论必须指到**具体行号**，且反向搜一次"这个变量被读过吗" |
| "`dh0` 不经过 `H_in`，所以 `H_in` 错时它应该好" | 数据流表 | 灌 golden `H_in` 后 `dh0` 变了 5 倍 | 数据流表要用**一次实验**对上 |
| "K=128 的 GEMM 收缩不准" | 依赖表 + "只有 dh0 好" | 仓库里早有 `M=128 rel=3.3e-4 PASS` 的记录 | **写假设前先 grep 自己的笔记找反例** |

三条共同的错法：**从代码/直觉读出因果链，然后把它当证据用**。
它们的自洽性检查（build 绿、测试绿、grep 无残留）在原理上都抓不到。

## 7. 收敛判据：什么时候可以停

| 条件 | 说明 |
|---|---|
| 目标形与弱配置都达标，且有 CONTROL 臂 | 可出"可引用"结论 |
| 只目标形达标、弱配置翻线 | 出"薄边界项"，附跨配置摆动范围 |
| 定位到机制但未修 | 记录"机制 + 未修 + 影响面"，不许写成"已解决" |
| 机制未闭环 | 记录"最小可复现现象 + 已排除项 + 下一步三个测试"，不许编解释 |
